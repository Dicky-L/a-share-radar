# 数据采集与部署运行手册

## 当前架构：无常驻后端

- Web: GitHub Pages 托管 `index.html`、`data/index.json`、`data/snapshots/YYYY-MM-DD.json`。
- 定时计算: `.github/workflows/collect.yml` 在 GitHub 托管运行器启动一次 Python，校验真实行情，提交有效 JSON，再通过同一工作流的 `deploy` job 发布 Pages。
- 行情: `collect.py` AKShare 获取股票代码列表，腾讯行情核验当天数据；接口失败/交易日未开市不会以模拟行情补齐。
- 频率: 北京时间 **工作日18:15**（UTC 10:15），是盘后快照，不是盘中实时行情，也不等同于18:00聊天日报。
- GitHub 计划触发可能延迟、偶发跳过，不能保证严格到分或持续运行。
- 节假日: 交易日历检查后跳过，页面沿用最后一个真实交易日快照，仍需注意显示日期。

## 日常用户怎样操作？

1. 打开 <https://dicky-l.github.io/a-share-radar/>。
2. 看页面上的“数据日期”和质量说明；如果与预期交易日不符，则视为旧数据。
3. 点击 **刷新已发布数据**，只会重新读取已发布 JSON，不会启动上游行情采集。
4. 在“股票搜索”查询当前快照；自选/持仓暂存浏览器本地。

## 手动排障

1. 到 <https://github.com/Dicky-L/a-share-radar/actions/workflows/collect.yml> 点击 **Run workflow**。
2. 查看 `collect` 的日志、`data/index.json` 的日期和 `data/snapshots` 是否有当天文件。
3. 如果出现新的有效快照，`deploy` job 自动更新 Pages；若当天文件未变化，则会跳过重复发布。
4. 如果故障持续，附上错误日志；不要把数据索引日期人工改成今天，更不要用旧日行情伪装成今日数据。
5. 仅修改网页时，`pages.yml` 的 Pages 工作流负责部署。

## 为什么不能只通过修改 cron 得到实时行情？

`collect.py` 目前明确只接受北京时间15:20后的**当日收盘价**（逐股报价时间要晚于14:55），因此即使增加10:00、11:00等定时触发，盘中也不会产出新快照。

若要“每小时行情”，需新增 `collect_intraday.py`，要求：
- 交易时段与午间休市校验；报价时间新鲜度校验；
- 每个交易日按 `YYYY-MM-DD/HHmm.json` 归档，收盘最终文件独立管理；
- 失败和部分股票不可用时，前端显示覆盖率和更新时间，不伪造完整市场成交额；
- 避免每小时把数千只股票大文件不断提交到 Git 仓库，长期更适合腾讯云 COS 存储；
- 浏览器读取的是最后一次采集的快照，不是真正“按访问时刻抓取”的实时查询。

## 后续实时服务架构

前端仍可用 GitHub Pages，腾讯云部署 FastAPI + Redis/PostgreSQL + 定时采集任务，浏览器通过 API 获取按权限可用的实时行情。密钥留在后端环境变量，且必须核实数据供应商的行情再分发授权。
